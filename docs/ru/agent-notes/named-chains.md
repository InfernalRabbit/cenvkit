# Именованные цепочки (`[name]`-секции и `--chain`)

Один `.cenvkit.envchain` может определять несколько **именованных цепочек**. Каждая
секция — полный список файлов Layer-1; `--chain <name>` выбирает одну на запуск.

## Формат файла

```
# строки до первого заголовка относятся к [default]
.secrets.env
.env
.${HOSTNAME}.env

[ci]
.env

[prod]
.secrets.env
.env
.prod.env

[db-external]
.secrets.env
.env
.docker-db-external.env
```

- Комментарии `#` и пустые строки игнорируются.
- Явный заголовок `[default]` эквивалентен неявному.
- Имена секций используются как есть; `--chain` без значения (или `default`)
  выбирает цепочку по умолчанию.

## Семантика (всё проверено)

| Свойство | Поведение |
|---|---|
| Наследование | **Нет.** Каждая секция самостоятельна; перечисляй все нужные файлы. |
| Порядок | last-wins. Более поздние файлы перекрывают более ранние по ключу. |
| Отсутствующие файлы | молча пропускаются (поэтому генерируемый/необязательный файл безопасно указывать). |
| Неизвестный `--chain` | exit **2**, в сообщении перечислены доступные секции (`default` не упоминается). |
| Пустая секция | пустая цепочка Layer-1; `compose`/validate тогда ставят `COMPOSE_DISABLE_ENV_FILE=1`, чтобы Docker не откатился к нативному `.env`. |
| Токены | `${ENV}`, `${CENVKIT_ENV}`, `${HOST}`, `${HOSTNAME}` подставляются и внутри записей секций. |
| Команды | `--chain` — persistent: `compose`, `env-files`, `validate`, `env-debug`, `gap-report`, `run`, `env`. `version`/`init` принимают его и игнорируют. |

`--chain` выбирает, **какие файлы** образуют цепочку. `--project-dir` выбирает,
**какой каталог** считается проектом. Они складываются:
`cenvkit --project-dir web --chain ci env-debug --files`.

## Зачем это нужно

У CI-раннера редко бывают те же файлы окружения, что у рабочей станции. Направить
гейт на изолированную секцию — значит держать `gap-report` честным вместо того,
чтобы он сообщал об отсутствии файлов:

```sh
cenvkit --chain ci gap-report          # что CI реально видит
cenvkit --chain prod compose config    # проверить деплой-цепочку
```

Деплой-цепочки — ещё и удобное место, чтобы положить сгенерированный env-файл
последним — так debug-вью совпадают с реальным запуском:

```
[prod]
.secrets.env
.env
data/.compiled.env      # генерируется; отсутствует => пропускается
```

## Ловушка приоритета

`last-wins` означает, что **закоммиченный шаблон побеждает секрет**, если оба
определяют один ключ и шаблон идёт позже:

```
.secrets.env   # API_KEY=real
.env           # API_KEY=CHANGE_ME  -> побеждает, потому что идёт позже
```

Для деплой-секций клади секреты **последними**. Для локальной цепочки, где `.env`
только *ссылается* на значение из `.secrets.env`, именно обратный порядок
(`.secrets.env` первым) заставляет интерполяцию `${VAR}` разрешиться — но тогда
дублированный ключ в `.env` молча переопределит секрет. Выбери один порядок и
держи ключи уникальными между тирами.

## Просмотр цепочки без печати секретов

```sh
cenvkit --chain ci env --format json | jq -r 'keys[]'   # только имена ключей
cenvkit --chain ci env-debug --files                   # только пути файлов
cenvkit --chain ci env-debug --json | jq '.files'      # резолвнутый список Layer-1
```

`env --format`/`env-debug --trace`/`env-debug --overview` печатают значения как
есть — держи их вне общих логов.
