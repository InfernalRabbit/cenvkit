# cenvkit — Go CLI

`cenvkit` — небольшой Go CLI, построенный на
**собственном загрузчике compose от Docker** (`github.com/compose-spec/compose-go/v2`,
закреплён `v2.17.0`). Он собирает `COMPOSE_ENV_FILES` из вашей **проектной env
chain** и делает `exec` в `docker compose`, а также поставляет **отладчик,
работающий без демона**, который объясняет, откуда берётся каждая переменная — и
помечает единственное место, где Compose молча вас кусает.

> Это **одностраничный справочник**. Полное сквозное руководство (настройка,
> монорепо, CI, устранение неполадок, рабочие примеры) — в [`guide.md`](guide.md).

## Что он делает и какой gap выявляет

Docker Compose намеренно держит два слоя раздельно:

| Слой | Что наполняет | Виден ли для `${VAR}` в YAML на этапе compose? |
|---|---|---|
| Проектное окружение (`COMPOSE_ENV_FILES` / `--env-file` / `.env`) | контекст интерполяции | **да** |
| `env_file:` сервиса | runtime-окружение контейнера | **нет** |

`cenvkit`:

1. **Собирает `COMPOSE_ENV_FILES` из вашей проектной env chain (Layer 1)** —
   с подставленными токенами, в объявленном порядке, секреты последними — так что
   `docker compose` интерполирует `${VAR}` против неё. Это **run-путь**
   (`cenvkit compose`/`env-files`).
2. **Оставляет сервисный `env_file:` только runtime** — в точности нативная
   семантика Docker, по сервисам, изолированно. cenvkit **не** вливает его в
   интерполяцию.
3. **`env-debug` обнаруживает и объясняет gap**: когда `${VAR}` в вашем YAML
   удовлетворяется *только* сервисным `env_file:`, реальный запуск откатывается к
   `:-default`. Отладчик говорит именно это — и то, как реально разрешается
   окружение контейнера каждого сервиса — целиком в процессе (без демона).

> **История.** Раньше cenvkit (и legacy-набор на `sh`) вливал каждый сервисный
> `env_file:` в `COMPOSE_ENV_FILES`, чтобы *закрыть* gap
> ([docker/compose#3435](https://github.com/docker/compose/issues/3435)). Это
> **отменено** (Layer-2-debug-only, 2026-06-17): сглаживание env_file каждого
> сервиса в одно глобальное пространство интерполяции схлопывало общие ключи
> (ловушка с коллизией `${PORT}`) и было неверным значением по умолчанию.
> Теперь `env_file:` — только runtime; gap **выявляется** отладчиком, а не
> замазывается молча во время запуска. Чтобы переменная питала интерполяцию,
> положите её в Layer-1 chain.

Построено на настоящем загрузчике (а не на legacy `awk`/`sed`): никакого
избыточного обнаружения по глобам (`include:`-граф авторитетен), `${SVC_DIR}` и
вложенные `${A:-${B:-c}}` разрешаются, нет вектора инъекции через `sed` (чистые
Go-строки; хостовые/env-токены whitelisted до `[A-Za-z0-9._-]`).

> Legacy-набор на POSIX-`sh` (`bin/`, `lib/`, `mk/`) **удалён**.
> `cenvkit` — единственная реализация.

## Как это работает

1. **Layer 1 — chain** (`internal/chain`, чистый Go). Читает `.cenvkit.envchain`
   (или значение по умолчанию `.env → .${CENVKIT_ENV}.env → .secrets.env`),
   подставляет `${ENV}`/`${CENVKIT_ENV}`/`${HOST}`/`${HOSTNAME}` (с санитизацией),
   оставляет файлы, которые существуют. **Это — и только это — `COMPOSE_ENV_FILES`
   для запуска**: контекст интерполяции.
2. **Перечисление сервисных `env_file:`** (`internal/engine`, единственный пакет,
   импортирующий compose-go). Загружает настоящий проект (`COMPOSE_FILE`,
   `include:`, профили, с затравкой из Layer-1) и перечисляет разрешённые пути
   `env_file:` активных сервисов. **Используется только `env-debug`** (детектором
   gap и runtime-представлением `--files`) — он **не** добавляется к
   `COMPOSE_ENV_FILES` для запуска.

## Установка

**Установленный** (рекомендуется):

```sh
go install github.com/InfernalRabbit/cenvkit/cmd/cenvkit@latest
# ephemeral, no install:
go run github.com/InfernalRabbit/cenvkit/cmd/cenvkit@latest <args>
```

**Вендоренный** (закоммитьте Go-модуль + POSIX-шим `cenvkit`; нужен тулчейн Go —
без закоммиченных бинарников, без сети):

```sh
./cenvkit <args>          # temp build in the tool's module; runs in your current directory
```

Для меньшей задержки на вызов в вендоренном режиме соберите один раз локальный
бинарник в gitignore и запускайте его:

```sh
go build -o .cenvkit.bin ./cmd/cenvkit   # .cenvkit.bin is gitignored
./.cenvkit.bin compose up
```

## Команды

| Команда | Что делает |
|---|---|
| `cenvkit compose <args>` | собрать Layer-1 chain, `exec docker compose <args>` (ядро) |
| `cenvkit env-files` | напечатать разрешённый `COMPOSE_ENV_FILES` (**только Layer 1**), по одному пути на строку |
| `cenvkit env-debug [--show VIEW]… [--var K] [--service S] [--json] [--redact]` | отладчик / детектор gap без демона; `--show` повторяется и каскадируется |
| `cenvkit gap-report [--json]` | CI/pre-build линт: код **1**, если любой `${VAR}` удовлетворяется только сервисным `env_file:`, **0** — чисто, **2** — compose-файл не найден (без демона) |
| `cenvkit run [-e ENV] [--expand\|--no-expand] [--print] -- <cmd> [args]` | запустить процесс с окружением из объединённой chain (без docker); пробрасывает код выхода дочернего процесса |
| `cenvkit env [-e ENV] [--expand\|--no-expand] [--format dotenv\|json\|shell]` | вывести окружение объединённой chain (только ключи из chain, отсортированы) для CI / скриптов / `eval` |
| `cenvkit validate [--all]` | `docker compose config -q`; `--all` валидирует и dev, и prod |
| `cenvkit init` | засеять `.X` из `example.X` (**no-clobber**), развернуть на один уровень каталогов |
| `cenvkit version` | напечатать версию |

Глобально: `--project-dir <dir>` (по умолчанию: текущий каталог) · `--chain <name>`
(именованная секция `[name]` файла `.cenvkit.envchain`; по умолчанию — список без
заголовка / `[default]`) · `--color auto|always|never` (по умолчанию `auto`).

**Цвет.** Человекочитаемый вывод цветной, когда stdout — терминал, и простой, когда
вывод идёт в пайп / файл. `--color=never` отключает, `--color=always` форсирует
(даже при пайпе). `NO_COLOR` (отключить) и `CLICOLOR_FORCE`/`FORCE_COLOR`
(форсировать) учитываются; CI трактуется как non-TTY (простой). **Вывод `--json`
никогда не цветной.**

`env-debug` **работает без демона** — он загружает модель в процессе через
compose-go, БЕЗ вызова `docker compose` через shell.

**Виды выводятся каскадом.** `--show` можно повторять, и секции идут в заданном
порядке (без `--show` — список Layer-1). Ничего не игнорируется молча: невозможная
комбинация даёт exit 2 с сообщением, чего не хватает.

| `--show …` | Что печатает |
|---|---|
| `list` | файлы Layer-1 chain (по умолчанию) |
| `files` | две группы: интерполяция (Layer 1) и runtime-only (пути `env_file:` сервисов) |
| `overview` | пофайловые слои: `+` новый / `~` переопределение (`old -> new`) / `·` повтор, сырые значения, строки `⚠ gap:` |
| `effective` | финальное окружение контейнера каждого сервиса с источником каждого значения |
| `trace` | история одной переменной (требует `--var`) |

`--value --var V` — не вид: печатает голое значение интерполяции и не комбинируется
с другими видами.

**Фильтры работают везде, где есть данные.**

| | `list` | `files` | `overview` | `effective` | `trace` | `json` |
|---|---|---|---|---|---|---|
| `--var KEY` | файлы, где объявлен | файлы, где объявлен | только его строки | только его запись | сама переменная | `vars` + записи |
| `--service S` | - | этот сервис | этот сервис | этот сервис | его эффекты | его блок |

Умолчания: `--var V` без вида подразумевает `--show trace`; `--service S` —
`--show effective`; `--json` без `--show` сохраняет исторический полный документ,
а `--json --show …` печатает только запрошенные секции.

Конфликты (exit 2, без тихого отката): `--value` с любым другим видом или с
`--json`; `--trace` / `--show trace` без `--var`; `--service` с набором видов, где
нет данных по сервисам. Устаревшие флаги одного вида (`--list`, `--files`,
`--overview`, `--effective`, `--trace`) остаются алиасами и предупреждают только в
человекочитаемом выводе, чтобы машинный оставался разбираемым.

`--redact` заменяет значения на `<redacted>`, сохраняя ключи, файлы и слои —
используй его при копировании вывода в тикеты или чат.
Эффекты `--trace` сообщаются **только для полей сервисов**
(`services.<name>.<field>`); `${VAR}` в top-level `networks:`/`volumes:`/`x-*`
вне области охвата (переменная всё равно попадает в атрибуцию chain, если это ключ
chain). Представление `--effective` никогда не сообщает разрешение, которого не
даст реальный запуск. Provenance использует собственные пакеты compose-go `dotenv`
+ `template` (паритет с docker-compose).

## `run` / `env` / `gap-report` — доставка и линт

Та же Layer-1 chain, что питает `compose`, управляет любым потребителем:

- **`run -- <cmd>`** сглаживает chain в объединённое окружение `KEY=VALUE` и
  запускает процесс с ним — без docker. `--expand` (по умолчанию) раскрывает
  `${VAR}` / `${VAR:-def}` через dotenv-движок compose-go (значения совпадают с
  `docker compose`); `--no-expand` оставляет их литерально. Окружение shell
  побеждает chain (паритет с compose). Коды выхода: код дочернего процесса, либо
  **127** — бинарник не найден / **126** — не исполняемый / **128+signo** при
  сигнале. `--print` печатает env и пропускает exec. `--` обязателен.
- **`env`** выводит то же объединённое окружение (только ключи из chain,
  отсортированы) в `--format dotenv` (по умолчанию) / `json` / `shell` — например,
  `eval "$(cenvkit env --format shell)"`.
  `cenvkit env --expand` == `env-debug --effective` == `docker compose config`
  (один движок раскрытия).
- **`gap-report`** — это CI/pre-build линт по тому же gap, который обнаруживает
  `env-debug`: код **1**, если какой-либо `${VAR}` есть только в env_file
  (переменная/сервис/поле/fallback; `--json` для инструментов), **0** — чисто,
  **2** — compose-файл не найден. Без демона — запускайте перед `docker build`.

`-e <env>` переопределяет `CENVKIT_ENV` на один вызов.

**`--env-file <path>`** (можно повторять; `env-debug`, `gap-report`, `env`, `run`)
добавляет env-файл **после** проектной цепочки, как `docker compose --env-file`: файл
участвует в интерполяции, поэтому переменная из него не считается гэпом, а
отсутствующий файл — ошибка (Compose тоже падает). `cenvkit compose` этот флаг не
забирает: docker-овский `--env-file` уходит в docker как есть.

> **Эти команды печатают значения дословно, включая секреты.** `env`,
> `run --print` и `env-debug --value|--trace` намеренно не редактируются (значение
> *и есть* ответ), поэтому не перенаправляйте их в общие CI-логи, тикеты или чат.
> cenvkit не управляет секретами, не маскирует и не шифрует их — см. примечание в
> разделе «Конфигурация».

- **`env_file:` — только runtime.** `${VAR}`, определённый *только* в сервисном
  `env_file:`, **не** разрешается при запуске — `docker compose` интерполирует
  `:-default` (нативный fallback). `env-debug --trace` помечает это как gap. Чтобы
  переменная питала интерполяцию `${VAR}`, положите её в **Layer-1 chain**.
- **Run-путь = только Layer 1.** `COMPOSE_ENV_FILES` (то, что задают
  `env-files`/`compose`) никогда не содержит путь сервисного `env_file:`.
- **Отсутствующий `env_file:`.** Отсутствующий *обязательный* `env_file:`
  лоялен при перечислении (поэтому `env-debug` никогда не падает) и
  **фатален в upstream при реальном запуске `docker compose`** (который заново
  применяет `required:`). cenvkit не перереализует семантику `required:` из
  upstream.
- **Секреты последними.** Гарантия **внутри Layer-1 chain** (`.secrets.env`
  выводится после остальных Layer-1 файлов; last-wins). Поскольку сервисный
  `env_file:` больше не питает интерполяцию, он **больше не может затереть
  переменную chain/секрет во время интерполяции**. (Во время выполнения каждый
  `env_file:` применяется только к своему контейнеру, нативно.)
- **Оверлеи `COMPOSE_FILE`** вида
  `docker-compose.yml:docker-compose.${CENVKIT_ENV}.yml` работают: cenvkit
  интерполирует `${CENVKIT_ENV}`/`${ENV}` и разбивает по
  `COMPOSE_PATH_SEPARATOR` (иначе — разделитель списка путей ОС; никогда `,`).
- **`COMPOSE_DEPTH`** принимается, но игнорируется (`include:`-граф делает
  обнаружение через глоб с ограничением глубины устаревшим). **Никакого
  избыточного обнаружения** — compose-файл не из `include:`-графа /
  `COMPOSE_FILE` не загружается; `.git` не важен.
- **`docker compose --env-file` моделируется по запросу.** cenvkit рассуждает о
  `COMPOSE_ENV_FILES`, `COMPOSE_FILE` и проектной chain; файл, переданный в
  docker через `--env-file`, неизвестен `env-debug`/`gap-report`, **пока** тот же
  путь не передан `cenvkit … --env-file` (или пока он не внесён в
  `.cenvkit.envchain`). `cenvkit compose` по-прежнему пробрасывает флаг.

## Конфигурация

- `.cenvkit.envchain` — Layer-1 chain (один шаблон пути на строку; комментарии `#`
  и пустые строки игнорируются). Может содержать необязательные **секции
  `[name]`**. Считайте его **доверенной конфигурацией проекта**, как `Makefile`:
  записи могут быть абсолютными или выходить за каталог проекта
  (`../shared.env`), и ничто не ограничивает их корнем проекта — та же свобода,
  которую Compose даёт `env_file:`. Поэтому запуск cenvkit на клоне, который вы не
  проверяли, позволяет этому файлу читать пути на вашей машине (их значения
  печатаются командой `env`). Проверьте его сначала или зафиксируйте
  `--project-dir` на дерево, которое контролируете.
- **Именованные chain** — `--chain <name>` выбирает секцию `[name]` (по умолчанию —
  список без заголовка / `[default]`). Автономны (без наследования), ортогональны
  `CENVKIT_ENV`; неизвестное имя завершает работу кодом 2 со списком доступных.
  Пустая секция даёт пустую chain, что отключает нативный fallback `.env` для
  `compose`/`validate`. Руководство:
  [`agent-notes/named-chains.md`](agent-notes/named-chains.md).
- Пустая выбранная chain отключает нативный fallback `.env` для
  `compose`/`validate`; она не наследует исключённые файлы. Явный `--env-file`
  Docker по-прежнему работает.
- `CENVKIT_ENV` — выбирает уровень окружения (shell > `CENVKIT_ENV=` из `.env` >
  `dev`).
- `COMPOSE_FILE`, `COMPOSE_PROFILES`, `HOSTNAME`/`HOST` — учитываются, как выше.
- **Секреты — вне области ответственности** — cenvkit никогда их не маскирует, не
  шифрует и не управляет ими; `.secrets.env` просто загружается последним
  (last-wins), на диск ничего не пишется. Оберните внешним менеджером:
  `sops exec-env -- cenvkit run -- <cmd>`.

## Архитектура / участие в разработке

- `cmd/cenvkit` — cobra CLI. `internal/chain` — Layer 1 (`COMPOSE_ENV_FILES`
  для запуска). `internal/engine` — перечисление сервисных `env_file:` для
  `env-debug` (**единственный** пакет, импортирующий compose-go; это проверяет
  seam-проверка в CI). `internal/envfiles` — merge/order/dedup.
  `internal/provenance` — модель env-debug + human/JSON-рендер, включая
  gap-детектор (чистый Go; `engine` импортирует его). `internal/bootstrap` —
  `cenvkit init`.
- Upstream-first: compose-go — источник истины для семантики compose; версия
  закреплена и поднимается осознанно (при подъёме перезапустите приёмку — см.
  чек-лист в §7 спецификации).
- Приёмка — это портированный smoke-набор `examples/monorepo` (`test/`); модель
  Layer-1/Layer-2, которую он фиксирует, описана в
  [`docs/ru/agent-notes/env-semantics.md`](agent-notes/env-semantics.md).
